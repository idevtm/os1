# os1 project review — 2026-11-11

This review is an independent, source-based audit of the complete `main` branch.
It covers boot, platform, memory, processes, syscalls, IPC, drivers, storage, user programs, the build system, and tests.
The main result: one critical defect lets any user process stop the machine, and QEMU reproduces it.
Two high-severity SMP lifetime races are in the process exit and wait path.
Reviewed source: `f1dbfb5eb99085fcfdc69ba6484dfaa6ddcaf489` on `main`, the merge of PR 51.

## Scope and method

This review examines the source as it exists on `main`, not only the last diff.
It does not change runtime code and does not implement corrections.
Third-party code under `third_party/` is out of scope, except for how project code calls it.

The coordinator exported `main` to a separate directory.
The coordinator ran six independent review agents with fresh context, and gave each agent one area.
Each agent had read-only access and reported evidence, severity, and status for each finding.
The coordinator examined the critical and high claims, and most medium claims, again in the source.
A separate document reviewer examined the remaining medium claims and a sample of low claims against the same revision.
The coordinator ran host tests, a kernel build, the normal-image QEMU suite, and one QEMU experiment.

## Critical and high defects

### R1: User code controls the GS base that every kernel entry uses

**Severity:** Critical. **Status:** Reproduced in QEMU (UEFI path).

**Location:**

- [`irqhandler.asm:22`](../../src/kernel/arch/x86_64/interrupt/irqhandler.asm#L22): `trap_entry_common` reads `[gs:CPU_CURRENT_THREAD]` first.
- [`irqhandler.asm:110-145`](../../src/kernel/arch/x86_64/interrupt/irqhandler.asm#L110-L145): `syscall_entry` reads and writes `[gs:...]` first.
- [`cpu.cpp:107`](../../src/kernel/arch/x86_64/cpu/cpu.cpp#L107): the user data descriptor is `SEGDESC64_DATA(3)` with base 0.
- [`cpu.cpp:181`](../../src/kernel/arch/x86_64/cpu/cpu.cpp#L181) and [`kernel_main.cpp:606`](../../src/kernel/core/kernel_main.cpp#L606): the kernel writes the per-CPU pointer to `IA32_GS_BASE` (`0xC0000101`) only at initialization.

**Trigger and impact:**
The kernel keeps the per-CPU pointer in `IA32_GS_BASE` while user code runs.
The source has no `swapgs` and no `IA32_KERNEL_GS_BASE`.
Ring 3 can load the DPL-3 selector `0x1b` into GS, which sets the GS base to 0.
The next syscall or interrupt then reads the current thread pointer near linear address 0.
User page tables do not map that address, so the access faults in ring 0.
Any unprivileged program can cause this; no rights are necessary.

The fault handler enters the same faulting path again, and the machine hangs or resets.
On the interrupt path, the nested faults use the kernel stack and can overflow into adjacent physical memory.
On the syscall path, the first `gs:` access at `irqhandler.asm:112` occurs before the stack switch at line 145.
Page faults do not use IST, so the CPU pushes the fault frames at the RSP value that user code selected.
The kernel does not enable SMAP, so these writes also succeed on a user stack.
If that value is a writable kernel address, the faults write to kernel memory (hypothesis; not tested).

**Evidence:**
A grep of `src/` for `swapgs`, `KERNEL_GS`, and `0xC0000102` finds nothing.
A scratch clone of `f1dbfb5` changed only `src/user/programs/fault.cpp`. The changed program writes a marker, runs `mov $0x1b,%ax; mov %ax,%gs`, and then calls `write`.
`ctest -R '^os1_smoke_spawn$'` failed after 60.11 s.
The last guest line was `[user/fault] boom`; the next marker and the shell never appeared, and the kernel printed no panic.
The same test passed with the unchanged program in the baseline run.

**Recommended correction:**
Use the standard `swapgs` discipline.
Keep the per-CPU pointer in `IA32_KERNEL_GS_BASE`.
Swap on every entry from CPL 3 and on every return to CPL 3.
Decide how NMI, `#DF`, and `#MC` on IST find the CPU record when entry occurs in the user-GS window.
Do not enable `CR4.FSGSBASE` until this design is complete.

**Missing validation:**
Add a QEMU user program that loads a user selector into GS and FS.
Let the program call a syscall and then wait for a timer tick.
Run the program on UEFI, BIOS, and SMP configurations.
In a scratch environment only, repeat the syscall case with RSP set to a kernel address.
Add a static check that each CPL 3 entry path does `swapgs` before its first `gs:` access.

### Exit-path interleavings (R2 and R3)

The diagram shows the two exit-path interleavings in R2 and R3.

```text
R2  CPU A (parent)                      BSP (reaper)
    waitpid: state = Blocked, enqueue
    release locks                       wake_child_waiters: dequeue parent
    still on parent kernel stack        write frame.rax, mark_thread_ready
    schedule_next ...                   CPU X restores the parent  <-- same stack on two CPUs

R3  BSP (reaper)                        CPU A (parent)
    clear_thread(last child thread)
                                        waitpid: Zombie, no threads -> reap_process (free)
    buffer_process_cleanup(owner)  <-- freed record
    owner->state != Zombie (freed or reused) -> reap_process(owner) again  <-- double free
```

### R2: A child exit can wake a parent that another CPU still runs

**Severity:** High. **Status:** Confirmed (code path; timing not reproduced).

**Location:**

- [`wait.cpp:156-165`](../../src/kernel/syscall/wait.cpp#L156-L165): the parent sets itself `Blocked`, enters the wait queue, and returns before it switches away.
- [`wait.cpp:195-213`](../../src/kernel/syscall/wait.cpp#L195-L213): `wake_child_waiters` writes `frame.rax` and calls `wake_blocked_thread`.
- [`thread.cpp:706-722`](../../src/kernel/proc/thread.cpp#L706-L722): `wake_blocked_thread` compares only with the current CPU thread.
- Correct guard in other wake paths: [`console_read.cpp:153`](../../src/kernel/syscall/console_read.cpp#L153), [`vfs.cpp:490`](../../src/kernel/syscall/vfs.cpp#L490), [`channel.cpp:1467`](../../src/kernel/ipc/channel.cpp#L1467).

**Trigger and impact:**
A parent on an AP calls `waitpid` for a child whose thread is still `Dying`.
The parent releases the locks and then switches away, but it still runs on its kernel stack.
At the same time, the BSP reaper dequeues the parent, writes its saved frame, and makes it runnable.
Another CPU can then restore the parent while the first CPU still uses the same kernel stack.
Possible results are corrupted kernel stacks, one thread on two CPUs at once, and incorrect `waitpid` results.

**Evidence:**
The console, VFS, and IPC wake paths all skip a thread that any CPU still has as `current_thread`.
The child-exit path does not.
[`ReaperSkipsDyingThreadStillCurrentOnAnotherCpu`](../../tests/host/proc/task_registry_tests.cpp) tests only the child case, not the parent case.

**Recommended correction:**
Move the rule "do not wake a thread that is current on any CPU" into `wake_blocked_thread` or `mark_thread_ready`.
Then keep or queue again a waiter that is still current, as the other paths do.

**Missing validation:**
Add a host test that uses `HostApCpuScope`, keeps the parent as the AP `current_thread`, and runs `reap_dead_threads`.
Add an SMP QEMU stress run with many short children and parent waits on APs.

### R3: The reaper uses a process that `waitpid` on another CPU can free

**Severity:** High. **Status:** Confirmed (code path; race not reproduced).

**Location:**

- [`reaper.cpp:70-85`](../../src/kernel/proc/reaper.cpp#L70-L85): after `clear_thread`, the reaper uses `owner` with no lock or lifetime pin.
- [`wait.cpp:126-180`](../../src/kernel/syscall/wait.cpp#L126-L180): `waitpid` reaps a `Zombie` child with no threads.
- [`process.cpp:115-117`](../../src/kernel/proc/process.cpp#L115-L117): `release_process_record` clears the record and frees it.

**Trigger and impact:**
The BSP reaper removes the last child thread with `clear_thread`.
From that point, `waitpid` on another CPU sees a `Zombie` with no threads and frees the process record.
The BSP still calls `buffer_process_cleanup(owner)` and `descriptor_close_all(owner->descriptors)`, and reads `owner->state` and `owner->parent`.
`owner->state` is no longer `Zombie` (the record is free, poisoned, or reused), so the reaper calls `reap_process(owner)` a second time.
With `OS1_KMEM_DEBUG`, this halts as a double free; without it, the second free can release a new process that uses the same memory.
`owner->parent` is also read without a lock, and a concurrent grandparent `waitpid` can free that parent.

**Evidence:**
The reaper takes `g_thread_registry_lock` only to select the thread.
`try_complete_or_block_wait_pid` uses `process_has_any_threads_locked` as its only gate, and `clear_thread` already removed the last thread.

**Recommended correction:**
Add a reap claim under `g_process_table_lock`.
Alternatively, let `waitpid` collect a child only after the reaper publishes "threads removed and cleanup complete".
Read and pin `parent` under the lock.

**Missing validation:**
Add a host test that interleaves `clear_thread` with `try_complete_or_block_wait_pid` through a test seam.
The test must confirm one release per process and clean `kmem` counters.

## Medium defects

### R4: Orphaned zombie processes are never reaped

**Severity:** Medium. **Status:** Confirmed.

**Location:**
[`process.cpp:120-134`](../../src/kernel/proc/process.cpp#L120-L134) (`orphan_children`), [`thread.cpp:769-770`](../../src/kernel/proc/thread.cpp#L769-L770), [`reaper.cpp:78-82`](../../src/kernel/proc/reaper.cpp#L78-L82), [`wait.cpp:16-21`](../../src/kernel/syscall/wait.cpp#L16-L21).

**Trigger and impact:**
A child that exits while its parent lives becomes `Zombie`.
When `reap_process` later removes the parent, from the reaper or from `waitpid`, `orphan_children` only sets `parent = nullptr`.
No code path reaps a `Zombie` without a parent, so the process record and its complete address space stay allocated.
A normal trigger: a program starts private providers and exits; the providers exit before the shell reaps the program.

**Evidence:**
In `src/kernel`, only `thread.cpp:770` sets `Zombie`, and only `reaper.cpp:78` and `wait.cpp:21` test for it.
No path changes a `Zombie` that has no parent.
The host test `ZombieProcessSurvivesThreadReapUntilWaitpidCanCollectIt` does not cover the orphaned case.

**Recommended correction:**
In `reap_process`, change each `Zombie` child to `Dying` and queue it for the reaper.
Also free the address space when the reaper removes the last thread (see [P4](#performance-and-resource-opportunities)).

**Missing validation:**
Add a host test: the child becomes `Zombie`, `waitpid` reaps the parent, and then the process registry must be empty.
Add a QEMU check that `process_count` returns to its baseline after the provider smokes.

### R5: Boot fails when firmware supplies 16 or more SSDTs

**Severity:** Medium. **Status:** Confirmed.

**Location:**
[`types.hpp:17`](../../src/kernel/platform/types.hpp#L17) (`kPlatformMaxAcpiDefinitionBlocks = 16`), [`acpica_integration.cpp:1256-1260`](../../src/kernel/platform/acpica_integration.cpp#L1256-L1260), [`acpi.cpp:204`](../../src/kernel/platform/acpi.cpp#L204), [`init.cpp:47-52`](../../src/kernel/platform/init.cpp#L47-L52).

**Trigger and impact:**
With 17 or more SSDTs, table discovery returns false.
With exactly 16 SSDTs, the DSDT uses one slot, and the 16th SSDT fails.
`platform_discover` then reports "ACPI required" and the kernel stops.
Machines with more than 16 SSDTs are plausible; this review did not collect table counts (see investigation item 4).
The array holds metadata only; `AcpiLoadTables` loads all tables independently.

**Recommended correction:**
Record the first entries and log a warning instead of failing.
Reserve one slot for the DSDT in the capacity given to discovery.

**Missing validation:**
Add host tests for table sets with 15, 16, and 17 SSDTs.

### R6: PCI INTx routes from `_PRT` use the wrong polarity and trigger mode

**Severity:** Medium. **Status:** Confirmed in code; the hardware effect is a hypothesis.

**Location:**
[`acpica_integration.cpp:772-784`](../../src/kernel/platform/acpica_integration.cpp#L772-L784), [`ioapic.cpp:67-94`](../../src/kernel/arch/x86_64/apic/ioapic.cpp#L67-L94), [`pci_msi.cpp:261-264`](../../src/kernel/platform/pci_msi.cpp#L261-L264).

**Trigger and impact:**
For a `_PRT` entry with a direct GSI source, the code returns `flags = 0`.
The IOAPIC code reads 0 as "conforming", which it programs as edge-triggered, active-high.
ACPI defines these PCI interrupts as level-triggered, active-low.
The kernel also never calls `\_PIC(1)`, so some firmware returns PIC-mode link routes.
A device that uses the INTx fallback can then get an interrupt storm or lose interrupts.
QEMU devices use MSI-X, so the current tests do not use this path.

**Recommended correction:**
Return level-triggered, active-low flags for GSI-sourced entries.
Call `\_PIC(1)` after namespace load and before route resolution; accept `AE_NOT_FOUND`.

**Missing validation:**
Add a host test of the flag output of `resolve_route_entry_irq`.
Add a QEMU run that disables MSI and MSI-X on one device.

### R7: Two-pass `observe` snapshots can write past the caller length

**Severity:** Medium. **Status:** Confirmed.

**Location:**
[`observe.cpp:248-300`](../../src/kernel/syscall/observe.cpp#L248-L300) (PROCESSES), and `observe.cpp:417-488`, `490-563`, `565-611` (DEVICES, RESOURCES, IRQS).

**Trigger and impact:**
The code counts records under the locks, releases them, checks the user length, and then takes the locks again.
The second pass writes one record per current entry and does not stop at the first count.
If a process starts on another CPU between the two passes, the kernel writes records past the declared length into adjacent caller memory.
If entries disappear, the header count is larger than the number of records written.
DEVICES, RESOURCES, and IRQS iterate with no lock and no bound.

**Recommended correction:**
Stop each second pass at the first count.
If fewer records exist, correct the header count.
A better correction is a copy into a bounded kernel array under one lock hold.
Then copy that array to the user with no lock held.

**Missing validation:**
Add a host test that adds a thread between the count and the copy.
The test must confirm that no byte after `length` changes.

### R8: Concurrent `observe(EVENTS)` calls share one global buffer

**Severity:** Medium. **Status:** Confirmed.

**Location:**
[`observe.cpp:706-745`](../../src/kernel/syscall/observe.cpp#L706-L745), [`smp.hpp:7-10`](../../src/kernel/sync/smp.hpp#L7-L10).

**Trigger and impact:**
`g_event_observe_snapshot` is a single static buffer of about 20 KiB with the `OS1_BSP_ONLY` label.
`sys_observe` runs on the CPU of the caller, and user threads run on APs.
The event-ring lock protects only the fill step; the copy to user memory occurs after the code releases the lock.
Two concurrent callers can get a header from one snapshot and records from the other.

**Recommended correction:**
Hold one lock across the snapshot and the copy, or copy in bounded chunks into a buffer for each call.
Remove the `OS1_BSP_ONLY` label.

**Missing validation:**
Add an SMP QEMU test with two concurrent event observers that checks sequence order and count consistency.

### R9: One process can use all 16 kernel bindings

**Severity:** Medium. **Status:** Confirmed.

**Location:**
[`channel.cpp:614`](../../src/kernel/ipc/channel.cpp#L614), [`ipc.h:182`](../../src/uapi/os1/ipc.h#L182), `kernel_provider.cpp:733-738`, `descriptor.cpp:21-36`.

**Trigger and impact:**
A Console binding needs only a console descriptor, and every process has descriptors 0–2.
A process that binds 16 times and keeps the clients uses the complete system limit.
After that, the shell and all other clients of Console, File, Directory, System, Log, and Input get `OS1_ERR_LIMIT`.
The [kernel console ABI](../native-api/abi/kernel-console-abi.md) documents the global limit, but not the missing per-process accounting.

**Recommended correction:**
Add a per-process binding quota in addition to the global limit, or charge bindings to an IPC account.

**Missing validation:**
Add a host test: process A holds 16 bindings, and the result for process B must follow the selected policy.

### R10: PS/2 function, keypad, Alt, and lock keys send control bytes

**Severity:** Medium. **Status:** Reproduced on the host with the source tables.

**Location:**
[`ps2_keyboard.cpp:24-82`](../../src/kernel/drivers/input/ps2_keyboard.cpp#L24-L82) (tables), [`ps2_keyboard.cpp:183`](../../src/kernel/drivers/input/ps2_keyboard.cpp#L183), [`console_input.cpp:125-148`](../../src/kernel/console/console_input.cpp#L125-L148).

**Trigger and impact:**
The tables use Linux keysym values such as `0xf1xx` for function keys and `0xf3xx` for keypad keys.
`key_to_char` returns `map[key] & 0xFF` for all keysym types, so these keys become C0 control bytes.
In canonical mode, F5 (`0x04`) commits the line as end of file.
F9 and NumLock (`0x08`) erase a character, and keypad `+` (`0x0a`) commits the line.
The F1–F12 terminal-switch hook does not consume the key, so F5 also sends end of file to the shell.

**Evidence:**
A host build of the source tables printed these values.
F5 → `0x04`, F4 → `0x03`, Left Alt → `0x03`, CapsLock → `0x07`, and Keypad 8 → `0x08`.

**Recommended correction:**
Return a byte only for Latin keysyms (`0xf0xx`, `0xfbxx`), and map keypad keys explicitly.
Let the terminal-switch hook consume its hotkeys.

**Missing validation:**
Add a host test over all 128 scancodes that rejects control bytes from keysyms that are not Latin.

### R11: A halted xHCI HID endpoint never recovers

**Severity:** Medium. **Status:** Confirmed path; the hardware frequency is a hypothesis.

**Location:**
[`xhci.cpp:795-813`](../../src/kernel/drivers/usb/xhci.cpp#L795-L813), `xhci.cpp:705-738`; Reset Endpoint occurs only in storage at `xhci.cpp:1282-1303`.

**Trigger and impact:**
A transaction error, babble, or stall on the interrupt IN endpoint halts the endpoint.
The driver drops the report and calls `arm_interrupt_transfer` without a check of the completion code.
A halted endpoint ignores the doorbell, so no event arrives again.
The input object stays connected without a removal event, and the keyboard or mouse stops working.
This can contribute to the xHCI receiver failures that the [input ABI](../native-api/abi/input-abi.md) records.

**Recommended correction:**
For a halting completion code, defer recovery to the worker thread.
Do Reset Endpoint, Set TR Dequeue Pointer, and `CLEAR_FEATURE(ENDPOINT_HALT)` with bounds, as EHCI `InputRecovery` does.
If recovery fails, remove the input and record the cause.

**Missing validation:**
Add a host test of the event handler for completion codes 4 (transaction error) and 6 (stall).

### R12: One EHCI transfer deadline retires the whole controller

**Severity:** Medium. **Status:** Confirmed path; device behavior is a hypothesis.

**Location:**
[`ehci.cpp:245-279`](../../src/kernel/drivers/usb/ehci.cpp#L245-L279); `retire(c)` is at [`ehci.cpp:277`](../../src/kernel/drivers/usb/ehci.cpp#L277).

**Trigger and impact:**
A device that sends NAK on a bulk transfer for more than about 1 s causes the deadline to expire.
A USB hard disk during spin-up is one example.
NAK sets no qTD error bit, so the root port stays connected.
The driver then retires the complete controller, which includes HID devices behind the same hub.
Recovery needs a reboot because the driver quarantines the controller DMA.

**Recommended correction:**
If the root port is still connected, stop the schedule and quarantine only the device.
Use a longer bulk deadline, as the xHCI storage path does.

**Missing validation:**
Add a host or QEMU fault case with a bulk endpoint that sends NAK for a long time.

### R13: xHCI timeouts count loop iterations, not time

**Severity:** Medium. **Status:** Hypothesis (timing not measured).

**Location:**
[`xhci.cpp:58-62`](../../src/kernel/drivers/usb/xhci.cpp#L58-L62), `xhci.cpp:885-903`, `943-954`, `963-993`.

**Trigger and impact:**
The command and transfer waits use 1,000,000 iterations of a lock, an event-ring scan, and `pause`.
The estimated duration is 10–50 ms, and it changes with the CPU.
USB 2.0 permits 50 ms for SET_ADDRESS and 500 ms for each data stage.

**Recommended correction:**

On a command timeout, abort the command ring instead of retiring the controller.

**Missing validation:**
Measure the iteration cost on the H81 desktop and on a current CPU.

### R14: A late AP can read the next CPU startup parameters

**Severity:** Medium. **Status:** Hypothesis.

**Location:**
[`cpu.cpp:250-270`](../../src/kernel/arch/x86_64/cpu/cpu.cpp#L250-L270), `cpu.cpp:18,30-43`, [`cpu_start.asm:71-77`](../../src/kernel/arch/x86_64/asm/cpu_start.asm#L71-L77).

**Trigger and impact:**
The AP sets `booted` only at the end of `enter_ap_idle_thread`.
The BSP waits for a fixed number of `pause` iterations.
After a timeout, the BSP writes the shared startup page, RIP, and CR3 slots for the next CPU.
A slow AP can then read the parameters of the next CPU, and two CPUs can share one `cpu` record and stack.
The AP that timed out also stays in the CPU list, and the scheduler can select it.

**Recommended correction:**
Let the AP acknowledge in the trampoline immediately after it copies its parameters.
Measure the timeout with the TSC or HPET.
After a timeout, send INIT to the AP and remove its record.

**Missing validation:**
Add a host test with a simulated slow AP, and a QEMU TCG `-smp 8` run with an injected delay.

### R15: The Limine shim writes fixed physical ranges without a memory-map check

**Severity:** Medium. **Status:** Hypothesis.

**Location:**
[`elf_loader.cpp:126-134`](../../src/boot/limine/elf_loader.cpp#L126-L134), `entry.cpp:258-269`, [`handoff_builder.cpp:317-342`](../../src/boot/limine/handoff_builder.cpp#L317-L342), `page_frame.cpp:79`.

**Trigger and impact:**
The shim writes the kernel segments, the boot CPU page, `BootInfo`, the boot stack, and the 512 KiB frame bitmap to fixed physical addresses.
It does not confirm that these ranges are `LIMINE_MEMMAP_USABLE`.
It does not confirm that they avoid the `kernel.elf` and initrd modules or Limine page tables.

**Recommended correction:**

Stop with a message if a range is not usable.

**Missing validation:**
Add a host test of range validation with synthetic memory maps.

### R16: A read-only virtio disk mounts writable and then blocks all disk reads

**Severity:** Medium. **Status:** Confirmed.

**Location:**
[`virtio_blk.cpp:598`](../../src/kernel/drivers/block/virtio_blk.cpp#L598), `virtio_blk.cpp:318`, [`block_device.hpp:43-54`](../../src/kernel/storage/block_device.hpp#L43-L54), [`fs/ext2.cpp:49-66`](../../src/kernel/fs/ext2.cpp#L49-L66), `fs/ext2.cpp:198-212`, `log_export.cpp:110-120`.

**Trigger and impact:**
The virtio driver detects `VIRTIO_BLK_F_RO` and rejects writes, but `BlockDevice` has no read-only field.
`ext2_mount` therefore mounts the device as writable.
The first mutation fails and sets `failed`; background log export can cause this mutation without user action.
After that, `read_block` rejects all reads, so `/disk` files and disk executables return `OS1_ERR_IO`.
Only the initrd rescue console stays usable.
USB mass storage already rejects write-protected media at initialization.

**Recommended correction:**
Add a read-only flag to `BlockDevice`.
Then reject the mount, or mount the volume read-only.
In read-only mode, return an access error for mutations and do not set `failed`.
Also let log export skip `/disk` on a read-only volume.

**Missing validation:**
Add a QEMU test with `-drive ...,readonly=on` and a valid ext2 image.

### R18: Init restarts a failing shell without limit and never starts rescue

**Severity:** Medium. **Status:** Confirmed.

### R19: `echo` with an opening parenthesis ignores redirection

**Severity:** Medium. **Status:** Confirmed by code trace; this review did not observe the exact error text.

**Location:**
[`command_engine.hpp:1614-1622`](../../src/user/include/os1/command_engine.hpp#L1614-L1622), `command_engine.hpp:1483-1490`, `sh.cpp:1593-1615`.

**Trigger and impact:**

**Missing validation:**

### R22: DMA registry snapshots race with allocation

**Severity:** Medium. **Status:** Confirmed read-side path; the write-side overflow is a hypothesis.

**Location:**
[`dma.cpp:162-168`](../../src/kernel/mm/dma.cpp#L162-L168), `dma.cpp:180-206`, [`dma.cpp:260-274`](../../src/kernel/mm/dma.cpp#L260-L274), `observe.cpp:99-111`, `observe.cpp:497-498`.

**Trigger and impact:**
`dma_allocation_records()` returns the shared snapshot pointer after it releases the lock.
`observe` then reads the count in a separate call.
A USB hotplug allocation on the worker can free and replace the snapshot during this interval.
The kernel can then copy freed or out-of-range heap memory to user space.
On the write side, the capacity check and the append use separate lock holds, so two allocators can exceed the capacity.

**Recommended correction:**
Reserve and append under one lock hold.
Copy records into a buffer owned by the caller while the lock is held.
Apply the same copy-out pattern to the PCI BAR and device-binding registries.

**Missing validation:**
Add a concurrency test of `observe` against DMA allocation.

### Limitations

- The coordinator did not run the diagnostic-image checks in `scripts/check-local.sh`.
- The R1 experiment ran only on the UEFI path with the default SMP configuration. The BIOS path is unmeasured.
- This review did not test physical hardware. R6, R11–R15, R27, and R53 need hardware or targeted QEMU evidence.
- No runtime test reproduced R2, R3, R7, R8, or R22. These need host test seams or SMP stress.
- Performance values in P1 and P2 are host I/O counts, not device latency.
- Each agent reported files it could not cover. The largest uncovered parts are most BIOS assembly, `acpica_ec.cpp`, `platform/hardware.cpp`, `interface/parameters.hpp`, `discovery/view.hpp`, most of `shell_runtime.hpp`, and image-builder scripts other than `write_usb.py` and `usb_data_image.py`.
- The complete ASD-STE100 Issue 9 dictionary was not available. This text follows the rules in [AGENTS.md](../../AGENTS.md#mandatory-documentation-standard); full compliance is not established.
